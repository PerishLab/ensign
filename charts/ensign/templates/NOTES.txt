ensign is installed.

Bootstrap, a separate finite Job, minted or reused the genesis sudo token and kept
it in a Secret. It is never printed and never re-minted; read it when you need
it:

  kubectl -n {{ .Release.Namespace }} get secret {{ .Release.Name }}-sudo \
    -o jsonpath='{.data.value}' | base64 -d

ensign creates both custody Secrets itself, through the api server. Helm never
owned them, so upgrade, rollback and uninstall cannot touch them — retention
needs no annotation. Deleting {{ .Release.Name }}-sudo by hand while the store
survives loses lockout recovery for good.

The store keeps its own pair. With the bundled PostgreSQL the chart generates
the password on first install and preserves it across upgrades; the data lives
in a StatefulSet volumeClaimTemplate, which Kubernetes leaves behind when the
release goes. So store and custody survive uninstall together — they stay a
matched pair. Wiping the store while sudo custody survives is recoverable: the
next bootstrap re-seals the vacant estate with the kept token. The reverse is
not: an occupied estate whose sudo Secret is gone cannot be bootstrapped.

Point at an external PostgreSQL with postgres.urlSecret.name and .key, and the
chart holds no credential at all.

Bootstrap uses its own ServiceAccount. The API ServiceAccount can get only
its named signing Secret; it cannot get sudo or create/list/update Secrets.
The binary also refuses sudo as a serving artifact.

Each Helm install, upgrade or rollback creates a revision-named ordinary
bootstrap Job. It retries a temporarily unavailable store with a six-retry
budget and a ten-minute deadline. This is not a hook: PostgreSQL and the Job
can start together without a pre-install missing-store or post-install Ready
cycle. Use --wait --wait-for-jobs --timeout 15m; inspect the Job on failure.
The API may restart until its prerequisites exist; serve verifies them and
never performs genesis. Retained custody is reused, not re-minted.

Helm 4 legacy RollingUpdate migrations use --server-side=false with upgrade.
Read the packaged README before upgrading; retain store and custody on refusal.

The API supports exactly one replica and uses Recreate. An update stops the
old API before starting its replacement, so plan for a brief availability gap.
This is update ordering, not fencing against forced Pod deletion or a lost
node. Rolling back to an older chart also restores that chart's permissions
and update strategy. The PostgreSQL and retained custody stay a matched pair.

Seed the first administrator with the cli, which reads sudo from stdin:

  kubectl -n {{ .Release.Namespace }} get secret {{ .Release.Name }}-sudo \
    -o jsonpath='{.data.value}' | base64 -d | ensign crown <login>

Sudo is the one pre-identity axiom. Use it to open the first invite and to
crown the first administrator, then leave it dormant for lockout recovery.

Only the api is routed. The web plane is deferred until its delivery paradigm
matures; it returns as an addition, not a migration.
